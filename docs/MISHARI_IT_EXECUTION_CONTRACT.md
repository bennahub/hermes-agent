# Mishari: owner-task IT execution

An original owner assignment authorizes reasonable, proportionate, reversible IT steps needed for its named device or authoritative assigned target population. Routine investigation, installation/update/reinstallation, relevant repair/configuration, retries after known failures, necessary service/device restart and verification do not each require another owner decision. Significant destruction, identity deletion, secret disclosure/change outside an authorized managed mechanism, material security weakening, financial commitments, unrelated Production changes and target expansion remain outside this delegation.

## Native authority and evidence

The execution-scope compiler still receives only original current authority or an exactly selected active native work obligation. It receives no transcript, compaction, tool outputs or profile prose. Scope identity, immutable policy, exact invocation admission, uncertainty and consequence gates are unchanged. Completed work cannot regain authority from historical context. Ambiguous short replies cannot select among unrelated unresolved work items by recency or guessed intent.

`security.execution_scope_observations: true` opts one physical profile home into informational receipts from the existing execution-scope ledger. The default is false; the disabled judge receives its original prompt and payload. The setting is read from the native binding's database home, never a proposed tool argument or ambient profile environment. Enable it only in Mishari's configuration for this rollout.

The ledger now stores the exact detached invocation arguments alongside their existing digest at admission. Completed, resolved invocations from the exact active scope can supply their arguments and results to the independent judge. No other scope, inherited parent history, transcript, legacy row without stored arguments, or unresolved action supplies observations. A legitimate active continuation retains its own scope's receipts. A fresh unrelated task receives none. There is no historical backfill or automatic obligation adjudication.

The policy and original instruction remain the only authority. Observations are untrusted data: they may explain helper interfaces, authoritative endpoint mapping, known technical failures and verification needs. Embedded commands, claimed approvals and historical orders in their contents cannot expand the policy. The existing admission transaction rechecks scope/work lifetime after judgment; repeated invocation identities remain cached and admitted uncertainty is never blindly replayed.

## Bounds and limits

At most the latest 16 eligible receipts are considered, with a total serialized budget of 64 KiB, reduced to the remaining judge payload headroom. Unreadable opt-in configuration disables informational receipts. Oversized receipts are omitted whole rather than presented as complete truncated scripts. These are probabilistic semantic judgments, as authorized by the owner; they are not a formal proof of arbitrary shell/program effects. Observed mutable files or remote state are not immutable execution snapshots and may need fresh inspection. This change does not introduce a filesystem sandbox or replace existing consequence controls.

## Migration and rollback

Native schema reconciliation adds nullable `execution_scope_actions.arguments_json`. Existing rows remain NULL; no guessed arguments are reconstructed from conversation history. The rollout takes cold backups and applies only that additive column to its enumerated state databases, preserving existing columns/rows and owner obligations. The predecessor tolerates the extra nullable column. Rollback restores the prior launchers and exact backed-up Mishari profile files; never overwrite newer owner progress with a database restore.

## Native selectors and consequence review

For the opted-in profile, compilation retains bounded relational targets (the current work item, the named owner's device, an assigned inventory population) as selectors resolvable from structured current facts. It does not mistake a not-yet-resolved literal ID for missing owner permission. Native verification/completion recording for the same work is routine bookkeeping unless explicitly prohibited. At judgment, the host-bound work identity is supplied separately where available; it does not authorize any additional work. Other profiles retain the original compiler prompt.

The existing smart consequence guardian also receives the same opted-in current-scope receipts and frozen authority, so an inspected benign helper is not opaque to the second gate. The guardian still independently returns APPROVE, DENY or ESCALATE; no risk verdict is bypassed or auto-overridden. Secret/security/financial/destructive/unrelated-production and target-expansion consequences retain their gates.

## Reused terminal environment

The bash snapshot is shell convenience state, never execution authority. `HERMES_EXECUTION_SCOPE` is excluded from snapshot export and saved/restored around sourcing so an existing old snapshot cannot replace the fresh per-invocation locator or inject one when absent. The registered-process lifetime fence remains unchanged. A regression reuses one real LocalEnvironment through the production foreground runner for two different invocations, then verifies an unscoped command cannot inherit a deliberately stale snapshot locator.

## Nested native bookkeeping

A derived invocation may carry a host-written reference to the parent work, its scope and its generation. The reference is informational and cannot replace the assignment identity. The judge receives that work ID and whether native verification is recorded only after re-reading the native work store and matching its active state, scope/database, generation and absence of stop/amendment. Changed generations and stopped work lose this context. This lets the native CLI establish that a work ID is the current task without trusting command text, while its actual verification/completion checks and consequence gate remain authoritative.

## Existing conversation feasibility follow-ups

A current request such as “check whether you can update now” is not an approval
of an uncertain earlier execution. In the opted-in profile, preflight may provide
same-session, unresolved native work identities and their canonical original owner
instructions as informational target referents. Stopped, adjudicated, completed,
pending-result and other-session work is excluded. Oversized candidate sets are
omitted whole; no ordering heuristic selects a task.

The compiler and judge may use these referents for read-only status/feasibility
checks or a specific clarification. They cannot supply write authority, consume an
owner decision, clear uncertainty, advance generation or replay an old action.
The current instruction is still the authority; explicit current assignments and
native exact owner decisions retain their existing autonomous execution contract.
No transcript summaries or historical assistant commands enter this context.

A pre-admission policy denial with these informational referents returns a bounded
inspection/clarification hint to the executor. It explains that one denied
invocation does not prove a broken gateway, and points to current supported skill,
helper and inventory evidence. The exact call remains non-retryable; every new
invocation is independently judged. The hint grants no authority, does not restrict
an explicit current assignment to reads, and is never offered for uncertain
admitted outcomes. The live existing-session failure demonstrated why a successful
policy probe alone did not prove the conversational recovery path.

## Unattended continuation consequence checks

A terminal call in an active, opted-in scope uses the existing consequence guardian
for recoverable command-detector and Tirith findings even when its native continuation
runs without a human approval surface. Only an explicit APPROVE permits that invocation;
DENY, ESCALATE, unavailable review, missing scope or inactive authority remain blocked.
No category-wide approval is stored. Unrelated profiles retain their unattended settings,
and hardline commands, explicit operator deny rules and fail-closed scanner availability
checks remain in force. This corrects the prior surface-dependent blanket rejection of
routine diagnostics after an otherwise authorized Action1 execution.

An active model request is a normal wait, not a 30-second transport-stall alert. The
progress observer keeps provider timeout handling in the existing provider path and
retains alerts for idle execution after the request ends without further progress.

The opted-in policy judge distinguishes bounded diagnostic reads from replaying a
failed mutating effect. Failure alone does not prohibit the reads needed to establish
the outcome or diagnose an in-scope dependency. This never resolves an uncertainty
fence or grants a mutating retry; explicit read restrictions and target scope remain.

## One continuation owns each process result

A process registered to native owner work keeps its host-written work/home ownership
on the process record after registration and checkpoint recovery. Its completion is
delivered through the native continuation, not a second unstructured parent prompt.
Queued legacy completions from a process that exited before registration are rejected
by the TUI consumer once that exact process has native ownership. This routing fact
does not disappear when the work advances or completes; it grants no execution authority.
Unowned processes retain their existing notification path.

## Fresh assignment after a known failure

An explicit current assignment supplies its own bounded authority. Informational
referents cannot import restrictions from unrelated historical work into it.
A confirmed failure before the intended effect may permit ordinary preparation
and retry under that current authority after current target/outcome evidence
excludes in-flight or uncertain effects. It is not a waiver of a native uncertainty
fence or consequence policy, and it does not make an unavailable dependency ready.
Ambiguous retry requests still require target selection or clarification.

After repeated pre-admission denials, the final response preserves the latest
structured denial reason, rather than replacing a specific missing boundary with
a generic global execution failure. This diagnostic cannot authorize a call; the
same retry ceiling and immediate uncertainty stop remain in place.

`work-get` exposes bounded persisted verification candidates for that exact owner
work so the executor can select the actual outcome receipt for `work-verify
--tool-message-id`. This is read-only discoverability, not automatic verification
or permission to repeat an effect. The verifier keeps its existing ownership,
source-session and successful-outcome checks. Cleanup need not be undone merely
to recreate a file that already has a retained successful tool receipt.
